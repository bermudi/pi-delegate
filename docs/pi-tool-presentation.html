How Pi Presents Tools to a Model

Yes—Pi mentions tools in prose in its default system prompt. But the full description and JSON schema are sent separately through the provider’s native tool/function field. These are two complementary channels, not one appended blob.

01 / 05

Background & Foundational Landscape

Mental model: advertisement versus protocol

A Pi tool has several fields, but they serve different audiences. The system prompt gets a terse human-language advertisement and behavioral guidelines. The API request gets a machine-readable protocol contract: name, full description, and parameter schema. The executable function remains inside Pi.

System prompt
“read: Read file contents”
Native tools field
description + JSON Schema
Local Pi runtime
validate + execute()

Prerequisites

  • JSON Schema describes valid structured data.
  • Modern model APIs support tool/function declarations outside ordinary chat text.

Context

The source of truth is each active Pi ToolDefinition. Pi uses selected fields to build its default system prompt, then passes stripped tool definitions into pi-ai, whose provider adapter serializes them for Anthropic, OpenAI, Google, and others.

02 / 05

Intuition Before Details

The core trick

Tell the model why and how in different layers. Prompt prose teaches tool-selection habits. A structured schema constrains the shape of a tool request.

High-level goal

Think of a restaurant menu plus an order form. The menu says “read—inspect a file” so the diner knows when it is useful. The order form has required box path and optional boxes offset and limit. The kitchen—the local execute() function—is not handed to the diner at all.

Expected outcome

The model can deliberately select a tool and emit arguments that software can parse. But schema support is not magic correctness: Pi still validates arguments before execution, because models can produce unknown names, malformed values, or semantically bad paths.

Literate Structural Breakdown

1. One tool definition contains three interfaces

return {
  name: "read",
  label: "read",                         // TUI-facing
  description: "Read the contents ...", // model API-facing
  promptSnippet: "Read file contents",  // system-prompt-facing
  promptGuidelines: [
    "Use read to examine files instead of cat or sed."
  ],                                     // system-prompt-facing
  parameters: readSchema,                // model API + validator
  async execute(id, args, signal, ...) { /* local code */ }
}

label and rendering helpers are for the terminal. execute is local capability. The model-facing pieces are deliberately split: a tiny snippet for prompt orientation, a full description for tool selection, and a schema for arguments.

Concrete delegate names

The delegate extension now names each layer by what it is:

const delegateTaskSchema = Type.Object({ ... });

const delegateArgumentsSchema = Type.Object({
  tasks: Type.Array(delegateTaskSchema),
  ...
});

type DelegateArguments = Static<typeof delegateArgumentsSchema>;

pi.registerTool({
  parameters: delegateArgumentsSchema,
  prepareArguments: normalizeDelegateArguments,
  execute(_id, args: DelegateArguments) { ... }
});

delegateTaskSchema is the nested schema for one array entry. delegateArgumentsSchema is the complete schema sent through the provider’s tools field. DelegateArguments is the validated TypeScript value shape. normalizeDelegateArguments is local pre-validation repair code; it is never shown to the model.

2. The default system prompt contains only the short listing

buildSystemPrompt() filters selected tools to those having a promptSnippet, then renders:

Available tools:
- read: Read file contents
- bash: Execute bash commands
- edit: Make precise file edits
- write: Write files

In addition to the tools above, you may have access to other custom tools...

Guidelines:
- Use read to examine files instead of cat or sed.
- ...
- Be concise in your responses

The JSON schema is not appended here. Nor is the long description. This prose is guidance, and it can mention strategy that schemas cannot express. Tool guidelines are deduplicated across active tools.

Subtle exception: if Pi uses a custom SYSTEM.md, buildSystemPrompt() returns that custom text plus context/skills/cwd. It does not synthesize the default “Available tools” list or tool guidelines. Active tools are still transmitted in the API’s structured tools field.

3. The generic model boundary strips away implementation

At the agent loop, active tools are reduced conceptually to:

{
  name: string,
  description: string,
  parameters: JSONSchema,
  constrainedSampling?: object
}

No JavaScript function crosses the network. The model cannot invoke your filesystem directly. It generates a structured request, and Pi decides whether and how to honor it.

4. Anthropic receives native tool objects

The Anthropic Messages adapter converts each generic tool to a top-level tools entry:

{
  model: "claude-...",
  system: [{ type: "text", text: systemPrompt }],
  messages: [...],
  tools: [{
    name: "read",
    description: "Read the contents of a file. Supports text files...",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "Path ..." },
        offset: { type: "number", description: "Line number ..." },
        limit: { type: "number", description: "Maximum ..." }
      },
      required: ["path"]
    }
  }]
}

Depending on model compatibility and tool metadata, Pi may also add Anthropic-specific flags such as strictness, eager input streaming, deferred loading, or cache control. Those are adapter details—not system-prompt text.

5. OpenAI receives function tools in its dialect

{
  instructions: systemPrompt,
  input: [...],
  tools: [{
    type: "function",
    name: "read",
    description: "Read the contents of a file. Supports text files...",
    parameters: { type: "object", properties: {...}, required: ["path"] },
    strict: false // capability/config dependent
  }]
}

Same semantics, different field names. Google similarly turns tools into function declarations. The provider—not Pi’s prompt text—gives these structured declarations special model-side treatment.

6. What the model returns

Rather than emitting ordinary prose like “please read a.ts,” a tool-capable provider returns a structured call, normalized by Pi to:

{ type: "toolCall", id: "call_123", name: "read",
  arguments: { path: "a.ts", offset: 1, limit: 2000 } }

The assistant message containing this call enters history. Pi finds the active tool by name, optionally prepares arguments, validates against the TypeBox/JSON schema, runs extension guards, and executes locally.

7. Tool output is a correlated message, not a new system instruction

{ role: "toolResult",
  toolCallId: "call_123",
  toolName: "read",
  content: [{ type: "text", text: "...file contents..." }],
  isError: false }

On the next model call, history includes both the assistant’s tool call and this matching result. Provider adapters translate that pair into their native tool-use/tool-result representation. This correlation prevents the model from confusing which result belongs to which call.

8. Schema guarantees syntax boundaries, not wisdom

The schema can require path and type limit as a number. It cannot guarantee that the chosen file is relevant, safe, or even present. Pi’s local validator catches malformed arguments; the implementation and extension hooks enforce operational policy; sandboxing or permissions enforce actual security.

The exact answer in one diagram

ToolDefinition
├─ promptSnippet + promptGuidelines → system prompt prose
├─ name + description + parameters → API tools/function schema
├─ parameters → local argument validation
└─ execute + label/rendering → stays inside Pi
