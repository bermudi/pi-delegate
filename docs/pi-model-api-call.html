Pi 0.83.0 · Textbook Chapter

What Pi Actually Sends to the Model

Pi does not send “the session.” It builds a fresh, provider-specific request from a generic three-part snapshot—system prompt, active transcript, and tool contracts—before every model turn.

01 / 05

Background & Foundational Landscape

Mental model

Pi is an agent loop around a stateless model API. The model does not remain alive inside your terminal, remember files, or execute tools. On each turn Pi takes its local state, translates it into a request, sends that request, records the response, optionally executes requested tools, then sends a new request containing the expanded history.

local session → generic LLM context → provider adapter → HTTPS payload
response → tool execution → local session → next payload

Prerequisites

  • An API call is stateless: continuity comes from resending relevant history.
  • A tool definition is a JSON schema the model can select; it is not the executable implementation.
  • “Tokens” are the model’s metered representation of all serialized instructions, history, schemas, and output.

Context

This chapter traces the installed Pi 0.83.0 path from AgentSession.prompt() through pi-agent-core and pi-ai. Exact wire JSON differs by API—Anthropic Messages, OpenAI Responses, Google, and others have different dialects—but Pi first constructs the same conceptual context:

{ systemPrompt: string, messages: Message[], tools: Tool[] }

Correction to the reductive model: “context files” are normally folded into the system prompt, not sent as file attachments. Files not read into a message or prompt are invisible to the model.

02 / 05

Intuition Before Details

The core trick

Reconstruct the model’s world on every call. Pi owns durable state; the provider receives only the carefully serialized snapshot needed for the next prediction.

High-level goal

Think of the model as an actor who forgets the play after every line. Before each line, Pi hands it a new script packet: the stage directions (system prompt), transcript so far (messages), and prop catalog (tool schemas). If the actor says “use the read prop,” Pi—not the actor—reads the file, adds the result to the transcript, and hands over a thicker packet.

Expected outcome

The terminal should feel continuous even though the network interaction is episodic. This explains three otherwise surprising facts: long chats cost more because history is resent; unread files do not exist to the model; and tool use normally requires at least two calls—one to request the tool and another to reason over its result.

Literate Structural Breakdown

1. User input is transformed before it becomes history

Pi first lets extension commands consume input. Then the input hook may replace it. A /skill:name command expands the full skill body into user text; prompt templates expand too. The internal result is multimodal:

{ role: "user", content: [
  { type: "text", text: expandedText },
  { type: "image", data: base64, mimeType: "image/png" } // optional
], timestamp }

The timestamp supports Pi’s state, but adapters need not send it. A slash command handled locally may generate no model call at all.

2. The “system prompt” is a compiled document

buildSystemPrompt() starts with Pi’s default coding-agent identity—or a custom SYSTEM.md that replaces it—then adds active-tool descriptions and guidelines, append-system text, project instructions, advertised skills, and the current working directory.

default or SYSTEM.md
+ active tool snippets/guidelines
+ APPEND_SYSTEM.md
+ <project_context>
    global AGENTS.md
    ancestor AGENTS.md files, root → cwd
  </project_context>
+ <available_skills> metadata only </available_skills>
+ Current working directory

Per directory Pi chooses the first of AGENTS.md, case variants, then CLAUDE.md. Skill bodies are normally not loaded here: only name, description, and path are advertised when read is active. The model must read the skill later, unless you invoked it directly.

3. Messages are a selected transcript, not the JSONL database

The active branch is rebuilt from Pi’s append-only session tree. User, assistant, and tool-result messages survive conversion. Pi-specific custom messages become user messages; local bash executions can become textual user messages. Error/aborted assistant replies are omitted during cross-provider replay.

messages = [
  user("Fix the parser"),
  assistant(text + toolCall("read", {path:"parser.ts"})),
  toolResult(callId, fileContents),
  assistant("The bug is ..."),
  user("Apply the fix")
]

Roles matter because providers train on conversational structure. A tool result is linked to the model’s tool call by ID; it is not merely pasted as free-floating prose.

4. Tools cross the boundary as contracts

Pi keeps the implementation locally. The model receives only name, description, and parameter schema (plus rare sampling metadata). For read, conceptually:

{ name: "read",
  description: "Read the contents of a file...",
  parameters: {
    type: "object",
    properties: { path: {type:"string"}, offset: {type:"number"}, limit: {type:"number"} },
    required: ["path"]
  }
}

When the model emits a structured tool call, Pi validates arguments, runs extension guards, executes local code, captures text/images/error state, and appends a toolResult. Then the loop calls the model again. Changing active tools also rebuilds the system prompt, keeping advertised capability aligned with actual schemas.

5. The generic snapshot is built before every call

Immediately before inference, extensions may transform a clone of the rich message context. Pi converts custom message types into portable LLM messages and calls its stream function with:

const llmContext = {
  systemPrompt: context.systemPrompt,
  messages: convertToLlm(transformContext(context.messages)),
  tools: context.tools
};
streamFunction(model, llmContext, { reasoning, headers, onPayload, ... });

This happens again after every tool result. Tools, model, thinking level, and system prompt may be refreshed between calls, but never mutate a request already streaming.

6. Provider adapters change the wire shape

Anthropic receives a top-level system block, alternating message content blocks, and tools[].input_schema. OpenAI Responses instead uses instructions, an input item stream, and function tools. Google uses its own systemInstruction, contents, and function declarations. “What Pi sends” therefore has two valid levels: the stable generic context and the provider-native payload.

// Anthropic-ish
{ model, system:[{type:"text",text:systemPrompt}],
  messages, tools:[{name,description,input_schema}], max_tokens, stream:true }

// OpenAI Responses-ish
{ model, instructions:systemPrompt, input:[...items],
  tools:[{type:"function",name,description,parameters}], stream:true }

Reasoning controls, cache markers, token limits, headers, image representations, and tool-call ID rules are adapter-specific. A before_provider_request extension hook can even replace the final native payload, so that hook is the literal last word.

7. Compaction replaces old active history with a summary

Pi does not blindly resend an unbounded transcript. Near the context limit it makes a separate summarization API call, stores the summary in the session, and constructs subsequent active history as:

user("The conversation history before this point was compacted...\n<summary>...</summary>")
+ retained recent messages
+ messages created afterward

Old events remain in the JSONL session file but leave the active model context. Compaction is lossy: the model now knows the summary, not every original token. Default policy reserves 16,384 tokens and attempts to keep 20,000 recent tokens.

8. What the model never receives automatically

  • The repository tree or file contents merely because Pi’s cwd is there.
  • Tool implementation code, UI details, or internal details metadata.
  • Every historical JSONL entry after branching or compaction.
  • Secrets unless some prompt, tool output, extension, or environment-aware provider mechanism exposes them.
  • Pi’s private “understanding.” Pi has orchestration state; the model has only payload tokens.
